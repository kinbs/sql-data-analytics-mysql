在本机 MySQL 8.0 上的完整落地

原仓库是一套基于 SQL Server 的 T-SQL 数据分析教学项目：先做探索性分析（EDA）， 再做趋势、累计、绩效、占比、分群等进阶分析，最后产出客户与产品两张报表。 本文档记录它在本机 MySQL 8.0 上被 1:1 重建、跑通、并对账验证的完整过程与结论。

00这个项目原本是什么，为什么不能直接跑

仓库里是 gold 层的三张表（客户维表、产品维表、销售事实表）加上 14 个分析脚本。原版全部依赖 SQL Server：BULK INSERT 导入、DATETRUNC 截断日期、TOP n 取前 N、 sys.databases 判断库是否存在，以及一个需要 SQL Server 2022+ 才能还原的 .bak 备份。

本机环境的三个硬约束：没有安装 SQL Server；没有管理员权限（装不了 Developer 版）； Docker Desktop 装了但 WSL 被安全策略禁用，Linux 容器起不来。
所以改用本机已在运行的 MySQL 8.0.44 作为执行引擎——数据模型、脚本逻辑、输出结果全部保持原样， 只做方言层改写。

01重建数据库

SQL Server 是「数据库 + schema」两级结构，MySQL 是「database 即 schema」一级结构。 原脚本里到处是 gold.dim_customers 这种两段式引用，所以直接把 database 命名为 gold， 这样 这些表引用一个字都不用改。

数据用 LOAD DATA INFILE 从 CSV 导入（MySQL 只允许从 secure_file_priv 目录读文件）。 源 CSV 里有空字段：17 个缺失生日、19 个缺失订单日期、7 个缺失产品分类， MySQL 严格模式会把空字符串当非法日期直接报错，所以用 NULLIF 显式转成 NULL， 与原表「空值即缺失」的业务含义保持一致。

导入校验通过：dim_customers 18,484 行 · dim_products 295 行 · fact_sales 60,398 行，与 CSV 记录数完全吻合。

02方言改写：12 处，逐条可查

原始脚本保持不动（03_scripts/），改写版单独放在 04_mysql/，每个文件头部都写了对应的映射说明。 其中两处最容易踩坑，单独解释一下：

① DATEDIFF 不是 TIMESTAMPDIFF

直觉上 DATEDIFF(MONTH, a, b) 应该翻成 TIMESTAMPDIFF(MONTH, a, b)， 但两者语义不同：SQL Server 数的是跨过的月份边界数（不看日），TIMESTAMPDIFF 数的是满月数。 比如 2021-01-20 到 2021-02-10，前者得 1，后者得 0。直接替换会让大批客户的 lifespan 少一个月。 所以改用 PERIOD_DIFF(DATE_FORMAT(b,'%Y%m'), DATE_FORMAT(a,'%Y%m'))，用 YYMM 相减，语义完全等价。 DATEDIFF(YEAR, ...) 同理，用 YEAR(b) - YEAR(a)。

② int / int 的截断行为

SQL Server 里两个 int 相除会截断小数（8249/3 = 2749），MySQL 的 / 返回小数。 为了让报表数值和官方快照一致，改写时用 DIV 复现截断。

04对账：改写是否真的等价

仓库自带了两张报表的官方快照 CSV（gold.report_customers.csv / gold.report_products.csv）， 这是最好的验收标准。我把 MySQL 生成的报表与它逐行逐列比对：

报表行数（官方 / MySQL）完全一致的列仅因日期变化的列不一致列
report_customers18,482 / 18,48211 列age、age_group、recency0
report_products130 / 13014 列recency_in_months0
结论：改写是可证明等价的。所有金额、数量、订单数、生命周期、分层标签、客单价、月均消费—— 逐字节一致。唯一不同的是 age 和 recency 这两类「跟着当天日期算」的列： 官方快照生成于 2025-01 左右，今天是 2026-10，偏移量恒为 21 个月（18482 行里最小值、最大值、中位数全部是 21）， 这条一致性正好反证了差异只来自「今天」，而不是逻辑错误。

业务高度集中在单一品类

自行车（Bikes）拿下 96.46% 的销售额，配件和服装加起来不到 4%。 这意味着营收对单一品类极度敏感——自行车的价格带或供应链波动，会直接放大到整体收入上。

市场分布：美国与澳大利亚几乎并列第一

两个市场贡献了超过一半的销售额，且体量接近；英国、德国、法国构成第二梯队。 这种「双核 + 长尾」的结构，适合把资源集中在两个主战场，同时用标准化方案覆盖长尾市场。

年度趋势：2013 年是一次明显的跃升

2011 与 2012 相对平稳（约 708 万 / 584 万）， 2013 年跳到 1,634 万， 是前一年的 2.8 倍。2010 和 2014 只有零星几天数据（首尾边界），不应参与同比判断。

月度走势

整体呈上行通道，且能看到明显的季节性起伏；用累计分析（脚本 08）可以看到累计线在每个年初重新起算。

排名：Top 与 Bottom 要看从哪张表出发

脚本 06 有一处很值得注意的教学点：从事实表出发做排名，只能看到「至少卖过一次」的产品； 从维表出发做 LEFT JOIN，才能把「一次都没卖出去」的产品揪出来——它们才是真正的垫底产品。 本例中确实存在销售额为 0 的在售 SKU，如果只看事实表就会完全漏掉。

06数据质量提示（原仓库自带，不是改写引入的）

  • 客户姓名是双重编码的乱码。源 CSV 里 Andrés 存成了 Andr┬®s 这类字节序列， 官方快照 CSV 里一模一样。要修的话得按 cp1252 → utf-8 重新转码，属于上游数据缺陷。
  • 19 行订单缺失 order_date。其中 2 位客户（key 5323、16040）的全部订单都没有日期， 会被 WHERE order_date IS NOT NULL 过滤掉，所以报表是 18482 行而不是 18484 行—— 官方快照同样是 18482 行，行为一致。
  • 17 位客户缺失生日，报表里 age 为 NULL、age_group 记为 n/a，与原逻辑一致。
  • 存在 110 岁的出生日期，明显是脏数据，原项目保留未处理。
  • 7 个产品缺失 category / subcategory，已按 NULL 处理，会单独成组出现在分组统计里。
